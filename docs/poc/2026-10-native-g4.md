# G4 — native scanner corpus parity and speed gate (2026-10)

Question: on large corpora, does the native (Rust) scanner give the same results as the JS scanner while meeting the design's T1 speed targets (49,332 files, cold scan median ≤ 2.0 s, cached ≤ 0.5 s)?

## Verdict

Pass. The first measurement failed, though; it passed after the directory walk was made parallel.

| Metric | Target | Result | Verdict |
|---|---|---|---|
| native cold scan median on the 49,332-file corpus (wall clock) | ≤ 2.0 s | 1.545 s | pass |
| native cached scan median on the same corpus (wall clock) | ≤ 0.5 s | 0.480 s | pass (20 ms margin) |
| same `names` set as JS on both corpora | identical | identical (byFile, files and unparsed identical too) | pass |

The cached scan has little margin (20 ms; 1 of 5 runs took 622 ms). Most of the remaining time is the directory walk (about 350 ms), and changing the thread count did not reduce it (see "Attempt log" below). The gate numbers are wall clock outside the `scanProject()` call, for both engines.

## Environment

- Apple M5 Pro (`sysctl -n machdep.cpu.brand_string`), `hw.ncpu` 18 (`hw.perflevel0.physicalcpu` 6, `hw.perflevel1.physicalcpu` 12), 48 GB memory.
- macOS (Darwin 25.5.0, arm64), Node v24.18.0, run with `pnpm exec tsx`. The native binary is `scanner.darwin-arm64.node` built with `pnpm build:native` (release, LTO).
- Scanner thread pool: default (number of cores = 18).
- Name set: `MATERIAL_SYMBOL_NAMES` + alias keys + legacy names (same as `scripts/bench-scan.ts`). No exclude patterns (the bench script default, same as G3).

## Corpora

| Corpus | Files | Description |
|---|---|---|
| synthetic (`scripts/gen-corpus.ts --files=50000 --seed=42`) | 50,000 | Publishable. 8 templates (JSX prop, menu array, type union, file without icons, ternary, template literal, style object, plain JS `flowish*.js`). 1,241 directories. |
| private | 49,332 | 12 copies of a private 4,111-file app (49,332 files). About 18.8 thousand directories. Used read-only. |

## Method

- `--runs=5` per engine. Each iteration deletes **the cache file the selected engine actually uses** (js: `.bench-cache.json`, native: `.bench-cache.native.json` as built by `nativeCacheFile()`), then scans once (cold) and immediately once more (warm).
- The script prints `cold: cache absent=true` / `warm: cache present=true` for each iteration. Every number below comes from runs where all 10 lines printed these values.
- Gate time is **wall clock**: for both engines, the `scanProject()` call is wrapped with `performance.now()`. It includes everything Metro actually pays (source existence checks, name set fingerprint, passing the names through napi and receiving the result, `Set`/`Map` conversion).
- The engine's internal time `ScanResult.ms` is recorded as a secondary figure. For JS it is wall clock inside the `scanProject` body, for native inside the Rust `scan_impl`, so the two engines measure different spans. It is therefore not used for the gate.
- To write nothing into the private corpus, `--cache-dir` puts the cache in a temporary directory outside it. The synthetic corpus uses the default (its root).

Commands:

```bash
C=$(mktemp -d) && pnpm exec tsx scripts/gen-corpus.ts "$C" --files=50000 --seed=42
pnpm exec tsx scripts/bench-scan.ts --runs=5 --scanner=js "$C" .
pnpm exec tsx scripts/bench-scan.ts --runs=5 --scanner=native "$C" .

# private corpus: one root as a single source "." (same arguments for both engines)
CACHE=$(mktemp -d)
pnpm exec tsx scripts/bench-scan.ts --runs=5 --scanner=js --cache-dir="$CACHE" <private-corpus> .
pnpm exec tsx scripts/bench-scan.ts --runs=5 --scanner=native --cache-dir="$CACHE" <private-corpus> .
```

| Engine | Corpus | files | names | unparsed | cold min / median (ms) | warm min / median (ms) | internal ms median cold / warm |

| native | private | 49,332 | 219 | 0 | 1523 / 1545 (1549, 1534, 1586, 1523, 1545) | 457 / 480 (494, 480, 457, 478, 622) | 1536 / 471 |
| js | synthetic | 50,000 | 3,710 | 0 | 3470 / 3640 (3755, 3640, 3859, 3503, 3470) | 350 / 354 (354, 353, 350, 363, 396) | 3640 / 353 |

For native, wall clock minus internal time is about 9 ms on the private corpus and about 25–30 ms on the synthetic one (the synthetic corpus has 31,250 byFile entries, so more result data crosses over). Of that, the name set fingerprint (SHA-1 over 4,213 sorted names) is about 0.5 ms. Measured separately, the rest is the cost of passing data through napi in both directions; caching would save almost nothing there, so it was left alone.

Speedup (JS wall clock median ÷ native wall clock median):

| Corpus | cold | warm |
|---|---|---|
| private | 3.7x | 3.0x |
| synthetic | 3.1x | 2.3x |

An earlier run the same day (internal ms only, same binary) gave native private cold 1492 / warm 458 and JS private cold 5407 / warm 1447. Results move by tens of ms with machine state. JS private cold varied widely in another run, 5400–8340 ms.

## Parity

- `test/parity/scan.parity.test.ts`: a 2,000-file synthetic corpus (`--seed=7`) plus walk-pruning fixtures. Icon names are put in `node_modules/`, `ios/` (top-level and nested), dot directories, symlinked files and directories (Unix, targets outside the corpus) and `DEFAULT_EXCLUDE` targets (`*.test.ts`, `__tests__/`, `*.stories.tsx`, root `dist/`). In both runs, default excludes and no excludes, names, byFile (after sorting), files and unparsed (run without a cache) are identical. The run without excludes has exactly 4 more files, which confirms the exclude patterns were actually applied. Deliberately disabling the Rust `node_modules` pruning was confirmed to make this test fail. It is part of `pnpm test`.
- On the 50,000-file synthetic corpus and the private corpus, both engines were run without a cache and the full results compared (one-off script, not committed), with no exclude patterns and with `DEFAULT_EXCLUDE`:

| Corpus | Exclude | files | names | byFile entries | byFile identical | unparsed |
|---|---|---|---|---|---|---|
| private | none | 49,332 | 219 | 6,624 | yes | 0 / 0 |
| private | default | 41,652 | 178 | 5,268 | yes | 0 / 0 |
| synthetic | none | 50,000 | 3,710 | 31,250 | yes | 0 / 0 |
| synthetic | default | 50,000 | 3,710 | 31,250 | yes | 0 / 0 |

None of the accepted differences (regex fallback for Flow syntax in `.js`, bracket nesting of 301 to about 750 levels, a few constructs only Rust parses) occurred in either corpus. No difference rule had to be added to the test.

## Attempt log (design §8 order)

All numbers in this section are engine-internal times (`ScanResult.ms`). They were taken before the switch to wall-clock measurement.

The first measurement failed the gate. It failed only on the private corpus and passed on the synthetic one; the difference was the number of directories (about 18.8 thousand vs 1,241). Temporary instrumentation (not committed) split `scan_impl` into phases and showed the walk took about 1 s both cold and warm.

| Step (private, native, 5 runs each) | cold median | warm median | walk (list) | file processing (process, cold) |
|---|---|---|---|---|
| Baseline: serial `walkdir` walk | 2102 ms (fail) | 1086 ms (fail) | about 970–1160 ms | about 1085 ms |
| ① parallel walk per directory | 1462 ms | 446 ms | about 340–380 ms | about 1075–1115 ms |

① uses the already-depended-on `rayon` instead of `jwalk` to read each directory's subdirectories in parallel (`native/src/walk.rs`, no new crate, `walkdir` dependency removed). The semantics are unchanged: the entry's own type (a symlink is neither a file nor a directory), exclude matching on root-relative `/` paths, pruning of ignored and dot directories, and a read error fails the scan. The caller sorts the result, and the error reported is the first one in directory-entry order.

② A `memchr` pre-filter was not tried. ① passed the gate, the remaining cold time is file processing (including parsing), and the pre-filter's own share was not measured separately.

③ Thread count (pool size changed through a temporary environment variable, 3 runs each, not committed):

| Threads | cold median | warm median | walk |
|---|---|---|---|
| 4 | 1866 ms | 500 ms | 420–530 ms |
| 6 | 1707 ms | 468 ms | about 390–400 ms |
| 8 | 1588 ms | 465 ms | about 385–405 ms |
| 12 | 1515 ms | 463 ms | about 355–370 ms |
| 18 (default) | 1467 ms | 442 ms | about 350 ms |
| 24 | 1470 ms | 451 ms | about 340–350 ms |

The walk stops improving at about 350 ms from 8 threads up (Estimated: a file system limit). The default (number of cores) was best, so it was kept.

Breakdown of the warm ~450 ms (temporary instrumentation): walk about 355 ms, cache read about 17 ms, stat about 55 ms, aggregation about 10 ms, cache-write check about 7 ms. oxc_semantic and stacker are inside the cold file-processing phase, and their share was not measured separately.

## Recheck after the unparsed re-extraction change (2026-10-03)

`scanProject` now re-extracts every file the native scanner reports as unparsed with the JS extractor, and the native scanner no longer caches unparsed files. Re-run on the private corpus with the release binary, `--runs=3 --scanner=native --cache-dir=<temp dir>`:

| Engine | Corpus | files | names | unparsed | cold min / median (ms) | warm min / median (ms) | internal ms median cold / warm |
|---|---|---|---|---|---|---|---|
| native | private | 49,332 | 219 | 0 | 1441 / 1531 (1681, 1441, 1531) | 451 / 458 (615, 458, 451) | 1523 / 450 |

The raw native scan (napi `scan`, before the JS re-extraction) reports 0 unparsed files on this corpus, so the re-extraction does no work here and the numbers are within run-to-run noise of the table above. Both gates still pass (cold 1.531 s ≤ 2.0 s, warm 0.458 s ≤ 0.5 s). The cost of the change grows with the number of files the native parser rejects (mostly Flow files): each one is read and parsed again by Babel on every scan, cold and warm. That cost was not measured on a Flow-heavy corpus.

## Paths not covered

- Linux and Windows binaries: measured only on this machine (macOS arm64). The directory walk may cost differently on other platforms.
- Cold OS cache: `purge` needs sudo and was not run. Every cold number is "no scanner cache" with a warm OS page and vnode cache. The first scan after a reboot can be slower.
- Slower machines (laptops with fewer cores): the warm margin is 20 ms of wall clock, so at a 4-thread level it is Estimated to exceed 500 ms (the ③ table above shows 500 ms internal time).
- Time inside a real Metro: measured only up to wall clock outside the `scanProject()` call. Metro startup and the registry write are not included.
