# G3 — project scan measurement (2026-10)

Question: is the Babel-based scanner (`scanProject` + per-file cache) fast and precise enough on a real monorepo, or do we need a Rust parser (oxc)?

## Setup

- Corpus: `git archive` of a pinned reference branch of a private production monorepo (React Native + web apps) (read-only), extracted into a `mktemp -d` directory that was removed afterwards.
- Paths archived: the `src` directories of three apps (called app A, B and C below; A is the largest, 4,111 files with the shared package) and of a shared UI package (`<shared-ui>/src`). App paths are shown as `<app-a>` etc.
- Machine: macOS (Darwin 25.5.0), Node v24.18.0, run via `pnpm exec tsx`.
- Name set: `MATERIAL_SYMBOL_NAMES` + alias keys + legacy names (same as `scripts/bench-scan.ts`).
- Each target was run 3 times (`--runs=3`). Cold = cache file deleted before the run. Warm = immediately following run with the cache present. Times are `ScanResult.ms` (wall clock inside `scanProject`).

Commands:

```bash
BENCH=$(mktemp -d)
git -C <private-monorepo> archive <pinned-reference-branch> \
  <app-a>/src <app-b>/src <app-c>/src <shared-ui>/src | tar -x -C "$BENCH"
pnpm exec tsx scripts/bench-scan.ts --runs=3 "$BENCH" <app-a>/src <shared-ui>/src
pnpm exec tsx scripts/bench-scan.ts --runs=3 "$BENCH" <app-b>/src <shared-ui>/src
pnpm exec tsx scripts/bench-scan.ts --runs=3 "$BENCH" <app-c>/src <shared-ui>/src
pnpm exec tsx scripts/bench-scan.ts --runs=1 --phases "$BENCH" <app-a>/src <shared-ui>/src   # x3
rm -rf "$BENCH"
```

|---|---|---|---|---|---|
| app A + shared UI | 4111 | 219 | 0 | 442 / 486 (649, 486, 442) | 105 / 110 (110, 110, 105) |
| app B + shared UI | 1705 | 125 | 0 | 201 / 253 (303, 253, 201) | 49 / 50 (50, 49, 56) |
| app C + shared UI (extra) | 2150 | 194 | 0 | 265 / 302 (521, 302, 265) | 47 / 47 (54, 47, 47) |

Note on spread: the first run of each process is the slowest (cold OS file cache and JIT). A separate 3-process series on app A gave cold 765 / 669 / 1172 ms, so "cold" varies by about 2x with machine state; all values stay far under the limit.

### Unparsed

0 files and 0 names for all three targets (nothing fell back to the regex path).

### Phase breakdown — one cold run, app A + shared UI (largest target)

Measured in `scripts/bench-scan.ts` only (the script re-runs the same steps as `scanProject` around exported `listSourceFiles` / `extractLiterals`, timing each with `performance.now()`; no timing code in `src/`). Three independent processes:

| Phase | run 1 (ms) | run 2 (ms) | run 3 (ms) |
|---|---|---|---|
| file listing (`listSourceFiles`, all sources) | 90.3 | 105.0 | 121.6 |
| read + stat (`statSync` + `readFileSync`, summed) | 248.7 | 300.8 | 391.5 |
| regex prefilter (summed) | 9.9 | 12.2 | 17.4 |
| `extractLiterals` (parse + walk, summed) | 113.7 | 141.1 | 188.7 |
| per-file loop total | 373.3 | 455.2 | 599.6 |
| parse share of (list + read/stat + prefilter + parse) | 24.6% | 25.2% | 26.2% |

Files: 4111 total, 587 parsed (14.3%), 3524 skipped by the prefilter (85.7%).
`scanProject`'s own `cold` for the same three processes was 765 / 669 / 1172 ms. It is larger than the phase sum because it also reads and writes the JSON cache and stats each file again; those costs are outside the phase table.

Reading: parsing is about a quarter of cold time; file I/O (read + stat, then listing) is about 70%. The prefilter already avoids parsing 86% of files. Even replacing the parser with an infinitely fast one would save only ~25% of cold time (about 0.1 to 0.2 s here).

## What this does not cover

- The monorepo's other apps were not scanned. Only apps A, B and C were measured.
- No `node_modules` or build-output directories are inside the corpus (the archive holds `src` only), so the cost of walking a project root that contains them is not measured. `node_modules`, `ios`, `android`, `Pods`, `coverage` and dot-dirs are skipped by name before descent.
- The corpus is a fresh extraction, so the OS file cache state differs from a developer machine at Metro start; the 765 to 1172 ms series shows the spread.
- Precision of `names` was not checked against ground truth. 219 includes literals that are valid icon names but plain words in app code (for example `function`, `window`, `select`, `light`, `123`, `abc`), plus names that appear only in `*.stories.tsx` files. Whether these are real usages was not verified; `exclude: ['**/*.stories.tsx']` would remove the story-only ones (not measured).
- Only the Babel path was measured; oxc was not benchmarked.
