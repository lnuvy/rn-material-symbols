# R0 — oxc API and napi-rs loading check (2026-10)

Question: can the native (Rust) scanner be built with the oxc parser + napi-rs? Pin the crate versions and API names that the later tasks (R1–R7) will use.

## Verdict

Pass. Both the oxc visitor API and napi-rs 3.x loading work. Two points must go into the design, though.

1. A Rust panic inside a `#[napi]` function does not become a JS error; it aborts the process. Every `#[napi]` entry point must use `std::panic::catch_unwind` itself.
2. The latest oxc (0.152.0) requires rustc 1.96 and this machine has 1.95, so 0.146.0 is used. Versions are pinned with `=`.

## Environment

- macOS (Darwin 25.5.0, arm64), rustc 1.95.0, Node v24.18.0, pnpm 10.
- All probes ran under `mktemp -d`; nothing was installed into the repository.

## oxc 0.146.0 API (compiled and run in the probe)

### Paths and signatures

- Visitor trait: `oxc_ast_visit::Visit<'a>` (`oxc_ast_visit` re-exports `generated::visit::*`). Entry point: `visit.visit_program(&ret.program)`.
- Default traversal functions: `walk::walk_*`, e.g. `oxc_ast_visit::walk::walk_function(self, it, flags)`.
- Fields of the parser's return value `ParserReturn<'a>`: `program`, `module_record`, `diagnostics`, `irregular_whitespaces`, `tokens`, `panicked` and others. The brief example's `ret.errors` does not exist in 0.146.0. Errors are checked with `ret.diagnostics.errors().count()` (or `ret.diagnostics.has_errors()`), fatal failure with `ret.panicked`.
- `visit_function` signature:

```rust
fn visit_function(&mut self, it: &oxc_ast::ast::Function<'a>, flags: oxc_syntax::scope::ScopeFlags)
```

`ScopeFlags` is `oxc_syntax::scope::ScopeFlags` (`oxc_ast` and `oxc_ast_visit` do not re-export it, so `oxc_syntax` must be added as a direct dependency).
- The type field of `Function` is `r#type: FunctionType`. The value `oxc_ast::ast::FunctionType::TSDeclareFunction` was confirmed. Other values: `FunctionDeclaration`, `FunctionExpression`, `TSEmptyBodyFunctionExpression`. There is also a `declare: bool` field.
- Skipping type positions, demonstrated: overriding `visit_function` to `return` on `TSDeclareFunction` gives `["skipdecl", "yes"]` for `declare function f(x: 'nodecl'): void; function g() { return 'yes'; }` (the `'nodecl'` inside the declaration is not visited).

| Probe | Input | Result |
| --- | --- | --- |
| basic | `type N = 'nope'; const x: N = 'home' as N;` (.ts) | 0 errors, strings `["nope", "home"]` (no type-position exclusion yet) |

(c) `.js`-family files containing JSX:

| How it was built | Result | module |
| --- | --- | --- |
| `SourceType::from_path("a.js")` | fails (1 error, panicked). `is_jsx()` is false | - |
| `SourceType::from_path("a.mjs")` / `("a.cjs")` | fails (same reason, `is_jsx()` false) | - |
| `SourceType::from_path("a.jsx")` | `is_jsx()` true | - |
| `SourceType::jsx()` | succeeds, `["home"]` | module |
| `SourceType::mjs()` / `SourceType::cjs()` | fails (JSX disabled) | - |
| `SourceType::from_path("a.js").unwrap().with_jsx(true)` | succeeds, `["home"]` | script (module=false) |

## napi-rs 3.x loading

- The minimal setup (the brief's Cargo.toml / build.rs / src/lib.rs / package.json) builds and loads.
- Build command: `npx --yes -p @napi-rs/cli@latest napi build --platform --release` (7.65 s). Outputs: `probe.darwin-arm64.node`, `index.js`, `index.d.ts`.
- Caution: the brief's `npx --yes @napi-rs/cli@latest build ...` fails with `npm error could not determine executable to run`. The package has two bins (`napi`, `napi-raw`) and npx cannot choose. Run it as `-p @napi-rs/cli@latest napi ...`, or install it as a dev dependency and use `napi ...`.
- Run: `require('./index.js').hello('rnms')` -> `hi rnms`.
- `Result<T>` return: `Err(napi::Error::from_reason("reason err"))` is thrown in JS as an `Error` (message `reason err`, code `GenericFailure`) and caught by `try/catch`.

### Panic behavior (important)

- Calling `#[napi] pub fn boom() -> String { panic!("kaboom from rust") }` does not produce a JS error; the process aborts. stderr shows `fatal runtime error: failed to initiate panic, error 5, aborting`, exit code 134 (SIGABRT). It cannot be caught with `try/catch`.
- Fix confirmed: wrapping in `std::panic::catch_unwind(|| ...)` and converting to `napi::Error::from_reason(...)` gives a catchable `Error` in JS and the process keeps running (`caught: true rust panic caught`, then `alive`). The panic message is also printed to stderr (default panic hook).
- Design consequence: every `#[napi]` entry point goes through a `catch_unwind` wrapper. Panics inside rayon parallel work must be caught outside the boundary the same way (R4). Unverified: whether a panic raised on a rayon thread propagates to the `catch_unwind` boundary was not checked in this probe.
